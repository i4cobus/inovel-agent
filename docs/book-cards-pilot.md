# 书卡试点：120 本（2026-10-09）

书卡是什么、为什么要它，见 `docs/agent-plan.md` 3.8。这里记试点的设置、速度、卡片长什么样、
为什么 v1 judge 的标签不能拿来验证，以及人工审阅怎么做。

## 设置

- 模型 Qwen3.5-9B（Ollama `qwen3.5:9b`，32K 上下文，关思考），输入是整份 digest
  （平均 12k 字、约 9k token，Ollama 日志确认没有截断），输出最多 700 token 的 JSON。
- 选书：646 本有 judge 标签的书按 `md5("cards:"+novel_id)` 对半分成验证半边（345 本 / 407 对）
  和保留半边（301 本 / 346 对，不参与调 prompt）。试点 120 本来自验证半边：60 本正例最多 +
  60 本负例最多，共 182 对（68 正例、114 负例）。`scripts/33b_select_card_pilot.py`，
  名单在 `eval/agent/cards_pilot_ids.txt`。
- 速度：**5.5 s 一张**（2 并发，Ollama 单路），120 张 656 s，0 解析错误，显存 8 GB。
  全量 7,655 本按此约 12 小时，可断点续跑（`data/cache/book_cards.jsonl`）。

## 卡片长什么样

描述类字段质量好，直接能用在检索和展示上。一张卡的样子（主角、背景、一句话、关键词是模型原话）：

> 题材 科幻；子类 无限流、同人；主角「高智商宅男穿越者，拥有系统辅助与动漫角色能力」；
> 背景「主神空间连接多个动漫世界的多元宇宙」；节奏 快；基调「轻松幽默，吐槽风，智斗为主」；
> 关键词 无限流、同人、动漫、系统、高智商、吐槽、穿越、主神空间……

120 张的分布：题材 都市 46、玄幻 19、历史 17、科幻 10；节奏 快 97、中等 20、慢热 3。
27 个标签 × 120 本 = 3,240 个判断：no 2,230、yes 677、unclear 333（10%）。

标签值分布暴露了模型的脾气：**内容类标签敢判，评价类标签不敢判**。

| 标签 | yes | no | unclear |
|---|---|---|---|
| 爽文 / 打脸 / 金手指 | 94 / 91 / 77 | 25 / 18 / 17 | 1 / 11 / 26 |
| 开挂 / 搞笑 / 速通 / 争霸 | 62 / 46 / 41 / 37 | 37 / 69 / 66 / 71 | 21 / 5 / 13 / 12 |
| 后宫 / 宠文 / 言情 / 玄幻 | 25 / 23 / 22 / 21 | 75 / 72 / 84 / 77 | 20 / 25 / 14 / 22 |
| 狗血 / 压抑 / 虐主 | 17 / 13 / 11 | 83 / 100 / 106 | 20 / 7 / 3 |
| 小白 / 独狼 / 种马 / 无脑 | 8 / 8 / 6 / 5 | 104 / 93 / 109 / 110 | 8 / 19 / 5 / 5 |
| **开局无敌 / 圣母 / 玛丽苏 / 恋爱脑** | **0 / 0 / 0 / 1** | 118 / 116 / 118 / 113 | 2 / 4 / 2 / 6 |

## v1 judge 的标签不再用于书卡

试点选书时用了 v1 judge 的 753 对约束标签，原打算拿它验证书卡的标签字段。复核后作废：

- 证据不同：v1 judge 看每本书 6 个 700 字的随机窗口，书卡看 digest，两边读的不是同一段文字。
- 定义不同：judge 按「负向排除项在摘录里出现即违规，不问是否主线」判 true/false；书卡按
  27 条词表定义判 yes/no/unclear。「圣母」「虐主」这类在 judge 那边是 700 字里出没出现，
  在书卡这边是全书特征。
- 模型和 prompt 不同：`gpt-5.6-terra` + `judge_v2`，为 v1 的相关性评分设计，和现在的 agent
  设计没有关系。

分歧没法归因到哪一边，所以那次对比的数字不记了（`eval/results/book_cards/` 里的 JSON 只是
试跑产物）。646 本的对半切分（`eval/agent/cards_label_split.json`）保留着，只用来固定
「哪些书可以拿来调 prompt、哪些书留到最后」。

## 人工审阅

验证改为人工：`scripts/37_card_review_page.py` 生成一个单文件 HTML（`data/review/card_review.html`，
不进 git），左边书单、中间书卡、右边 digest 原文。120 本里按 `md5("review:"+novel_id)` 稳定
抽 30 本标为「抽样」。每本可以标：六个描述字段对 / 部分对 / 错；每个判 yes 或 unclear 的标签
✓ 或 ✗；卡片漏掉的标签；备注。结果存在浏览器里，可导出 JSON 回收到仓库
（`eval/results/book_cards/manual_review.json`，待审完提交）。

## 决定

1. **卡片的描述字段（题材、子类、主角、背景、基调、一句话、关键词）先按能用处理**：作为第 12 段进
   多向量索引再池化，看检索基准动不动；`search_books` 的候选预览换成一句话 + 关键词。
2. **标签字段分两类用。** 内容类（爽文、打脸、金手指、开挂、争霸、魔改、狗血、搞笑、速通、
   灵异、后宫、种马、宠文、言情、玄幻、超能力、克苏鲁、宫斗、独狼）：卡片的 yes / no 可以
   直接当 `check_trope` 的第一层答案，省掉一次采样判定。评价类（圣母、小白、无脑、恋爱脑、
   开局无敌、玛丽苏、虐主、压抑）：卡片的 no 不可信，一律当 unclear，仍走采样正文判定。
3. **全量建卡**：12 小时 PC 时间，可断点续跑；建不建由人定。不建的替代是只给被检索到的书
   现场建卡，5.5 s 一本，agent 一轮前 20 个候选要 2 分钟，太慢，不取。
4. **标签字段的可信度以人工审阅为准**，审完 30 本再定内容类 / 评价类的分法对不对。
