## 第 1 轮暴露的问题与改动

1. **finish 被截断**：每步完成 token 上限 1,024，长回答加推荐列表超过它，参数变成非法 JSON，58 个会话里 9 个撞上。上限改 4,096，错误提示里写明「可能超长被截断」。
2. **只陈述偏好的消息没有 finish**（Plus 3 次 `answer_without_finish`）：提示改成每一轮都以 finish 结束，写完记忆用 `asks_user=true` 问用户想看什么；nudge 文案同步。
3. **标签类负向没逐本 check_trope**：两个模型都倾向于读 get_profile 的书卡就当核查过。提示明确「每个标签类负向、每本推荐书都要调一次 check_trope（它先查卡，几乎不花时间）」。Flash 的覆盖从 0.71 到 0.89，Plus 从 0.13 到 0.43。
4. **把元素当题材**（`genre="种田经营"`，Flash 每轮 5 次）：过滤器现在直接回「是元素，不是题材，放进 elements」，模型下一步就改对。
5. **评分规则错误**：记忆任务的会话若没写 `must_pass`，评分回退到任务级负向词，于是 oneoff 变体的第二个会话被要求继续核查上一轮的一次性条件，按构造必失败。改为按会话自己的期望评分；同一句话里持久化的词在本轮也算约束。

## 怎么选

Flash 在工具协议上更听话：finish 率 1.0、check_trope 覆盖更高、无 budget 耗尽；Plus 第二轮记忆类 6/6 全过，但约束推荐 14 条里仍有 2 条没给出推荐、2 条没以 finish 结束，标签核查覆盖只有 0.43。
dev 只有 20 条，一条任务等于 5 个百分点，0.75 对 0.70 本身分不出高下；分得出的是协议遵守和费用：Flash 一轮约 ¥1.2，Plus 约 ¥3.4。

结论（用户 2026-10-12 拍板）：主模型用 Qwen3.8-Flash；对照 arm 只留本地 Qwen3.5-9B，Plus 不再跑。

## 界面首轮（2026-10-12 晚，真实索引 + Flash）暴露的提示问题

两条真实对话（凡人流仙侠 / 克苏鲁 + 推理悬疑，轨迹在 PC `data/sessions/`）又暴露了四处，都是提示词与工具描述的问题，当晚改掉（commit 见 git log）：

1. **核查没人提的标签**：新会话、记忆为空、请求里没有负向条件，模型仍对一本书调了 `check_term(["后宫"])`。原因是「后宫」在系统提示和 `check_trope` 描述里出现了四次，全是示例。改法：示例去掉，明写「只核查用户这次说了的或记忆里记着的负向条件，没有负向条件就不用这两个工具」。
2. **用 check_trope 确认正向要求**：`check_trope("推理悬疑")` 返回 `unknown_trope`。改法：工具描述里列出全部 27 个可判标签，提示说明正向要求靠过滤、书卡和 get_profile 判断。
3. **过滤值瞎填**：`elements=["宗门"]` 不在词表（工具描述已附词表，错误也列了可用值）。提示补一句：不在列表的概念写进 query。
4. **推荐理由带工具名**：reason 里出现「check_trope(后宫)=no；感情线=无」。finish 的 reason 描述和提示都改为「用用户能懂的话，不写工具名和内部结果」。

另外界面侧：书名模型自带《》，卡片不再重复包一层；会话只重放最近 8 轮。

## test 后的三处修正（2026-10-26，待 dev 验证）

test（`docs/agent-test.md`）归因出的三类模型失误，改法各不相同，都不碰 test 的任务集：

1. **核了却照推**（rec-069 / rec-081）：提示里明写「判为违反的书不能进 recommendations」；另外在 loop 里加一道硬门：本轮 `check_term` 返回 `violates: true` 或 `check_trope` 返回 `yes` 的书，若出现在 finish 的 recommendations 里，finish 被拒一次，错误信息复述证据，要求换书或说明；同一本书第二次提交就放行（给「核查的其实是用户想要的元素」留出口，也不会死循环）。`AgentConfig.refuse_violating_recommendations` 可关。代价：触发时多花一步。
2. **换题材后忘了核记忆里的条件**（mem-003 / mem-012）：提示里把负向条件的来源写成两个（当场说的 + 长期记忆的「不要」项），并说明换题材、换一轮也要对每本新书核；长期记忆块的标题同样加了这句。
3. **只写记忆不 finish**（mem-016，nudge 之后仍只回文字）：某一步只调了 memory_write / memory_read / set_aside 时，下一步前的系统提示由「还剩 N 步」换成「记忆已更新，直接用 finish 结束」；nudge 文案改成「把刚才那段话放进 finish 的 answer」。

`max_steps` 维持 10，第 4 项（mixed 任务步数偏紧）这轮不动，便于归因。验证：dev 20 条、Flash、与第二轮 dev 同配置，比较 0.75。

### dev 第三轮（dev-flash-03，2026-10-26）：0.55，两处是新改动引入的回归

同配置（Flash、6 并发、`max_steps` 10），通过率 0.55（约束推荐 0.50、记忆 0.67），finish 率 1.0，规则违反率 0，步数 5.3、提示 token 37.8k（第二轮 6.5 步、47.1k）。逐任务对比第二轮：修好 2 条（rec-047、rec-110），退步 6 条。退步的归因：

- **rec-033、rec-065（新改动引入）**：模型第一步只调了 `memory_read`，「记忆已更新，直接 finish」的提示照样触发，模型照办，两步结束、零推荐。改法：提示只在 `memory_write` / `set_aside` 之后出现，不计 `memory_read`；文案改成条件式，「用户这次还提了找书要求就继续处理」。
- **rec-064（旧 bug，这轮撞上）**：模型把 `recommendations` 传成 JSON 字符串，loop 的 `list()` 把它拆成 418 个字符，评分当作无推荐。改法：字符串按 JSON 解析，不是对象数组就以错误退回让模型改。
- **rec-125（硬门按设计工作）**：《商业枭雄》check_term 返回「系统」密度 12.1、`violates: true`，finish 被拒，模型随后换了两轮检索仍凑不够 3 本，10 步耗尽后交付零推荐并解释了每本为什么不行。第二轮同一任务推荐的三本没有经过这道门。行为是对的，分数是步数预算的问题（见第 4 项）。
- **rec-049**：推荐里一个 novel_id 抄错一位（4fe2b724 对 4fe25b72），`ungrounded_id`。模型抄写错误，任何一轮都可能出现；可以考虑在 finish 处校验 id 是否出现在本轮工具结果里。
- **rec-126、mem-014**：漏核一本，和以前的 tool_skipped 同类。

硬门这轮触发 3 次（mem-007、mem-009、rec-125），前两次模型都换了书、任务照常通过；提示修改本身没有产生新的失败形态。两处回归已改（含测试），待再跑一轮 dev。

### dev 第四轮（dev-flash-04，2026-10-26）：0.80，三处修正定稿

两处回归修掉后再跑一轮，同配置：通过率 **0.80**（约束推荐 0.79、记忆 0.83），finish 率 1.0，规则违反率 0，check_term 覆盖 0.98、check_trope 覆盖 0.96（第二轮 0.88 / 0.89），步数 6.1、提示 token 43.7k（第二轮 6.5、47.1k）。第三轮退步的 6 条全部回到通过。

剩下 4 条失败：

- `rec-088`、`mem-007`：漏核一本，和第二轮同两条，从第一轮起就没过。
- `rec-033`、`rec-125`：硬门各拒了一本（《王牌》「系统」密度 10.2；《万亿市值不是梦》「系统」密度 5.4），模型没换到第三本，交付两本并说明。两条的共同点：用户的负向是「修仙」「金手指」，模型把「系统」当作它们的代理词去核了，这正是 test 里统计的「未经请求的核查」里的同义扩展；硬门不区分这个词是不是用户说的，所以扩展核查的代价从多一次调用变成了少一本书。错误信息留了「说明后再次 finish」的口子，模型两次都没用。

硬门本轮触发 3 次（rec-065 的《百炼成仙》僵尸密度 9.7 被拒后模型换书、任务通过），加上第三轮的 3 次，6 次里 4 次换书成功。记忆写入后的 finish 提示触发 8 次，没有再出现只回文字不 finish 的会话，也没有再出现写完记忆就不找书的会话。

**结论**：三处修正保留。dev 从 0.75 到 0.80 在一条任务的噪声内，分得出的是覆盖率（0.88 / 0.89 → 0.98 / 0.96）和失败形态：第二轮的失败是「没核」，这一轮的失败是「核了、被拒、没凑够」，后者是预算和扩展核查的问题，归到下一步：压「未经请求的核查」里的同义扩展，和 `max_steps` 10 → 12 的 dev 对比。test 不重跑，Flash 的 test 数字仍是 0.867（commit 4c0ca3b 的提示）。

打分这轮改了四处，都是对照轨迹发现的：答案类指标要用完整轨迹（脱敏文件把 answer 指纹化了，`load_run` 现在优先读本机 `data/eval_runs/<run>/`）；模型引用 ask_book 返回的「简介」「章节目录」段落时算真实引用而不是编造；开头类问题可以只靠 get_profile（档案就是开头摘录）回答，算找对书、算取到；拒答措辞加了几种真实出现的说法（「没法告诉你」「不在收录范围内」「不想凭书名猜」）。

约束推荐的失败仍是老两样：漏核一本、推荐数不够。没有新的失败形态，提示不动，下一步直接跑完整 test。
